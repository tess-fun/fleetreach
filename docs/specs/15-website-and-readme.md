# Spec 15: Website, docs and README rebuild

Status: implemented (website/, Astro Starlight) · Owner: website · Depends on: nothing (1.5.0 features are on main)

The site today is one hand-written landing page (`site/index.html`) plus a 13-page mdBook
(`docs-src/`, ~1,500 lines) and a 600-line README that carries most of the reference. It
under-sells the product: since 1.0 we added SBOMs (CycloneDX and SPDX), licenses, SSVC and
repo context, fix plan/apply/verify, history/SLAs/notify, the HTML report, VEX, novelty and
release-age signals, fleet sources (GitHub, GitLab), and Maven resolution. None of it has an
example page, a use-case page or an integration page, and nothing is shaped for search
engines or LLM retrieval (no sitemap, no llms.txt, no per-page markdown, no structured data).

## What the best projects do (survey, 2026-11-01)

Looked at: uv, Ruff, Bun, Biome, Deno, ripgrep (general dev tools) and Trivy, OSV-Scanner,
Renovate, Semgrep (our category).

1. **Install above the fold, one line, OS tabs**, then one first command. Repeated in the
   final call to action (Bun, Biome, Deno, uv).
2. **Real transcripts, not prose.** `$ command` followed by the actual output (uv, Bun);
   before/after with real diagnostics (Biome). Snippets carry filename labels.
3. **Proof with a reproduction link.** Bun's benchmark charts each link to the bench folder
   and state the method. Our equivalent is accuracy, not speed: the 1.5.0 oracle validation.
4. **"Replaces X / pairs with Y" stated inline**, plus a few dedicated comparison pages
   (Semgrep has five: CodeQL, Snyk, SonarQube...; Renovate has bot-comparison).
5. **Integrations as their own section.** uv has 17 integration guides (Docker, GitHub
   Actions, GitLab CI, Renovate, Dependabot...). OSV-Scanner has one, and it shows.
6. **Diátaxis-shaped docs**: Getting started, Guides (task), Concepts (why), Reference
   (generated: one page per command, settings, env vars). uv is the cleanest example.
7. **Machine-readable entry points**: uv and Semgrep serve `/llms.txt` and a markdown copy of
   every page (`…/index.md`, `….md`), plus a sitemap with `lastmod`. Trivy, OSV-Scanner and
   Renovate have no llms.txt; Trivy and OSV-Scanner have no sitemap. That is an opening.
8. **The README is a storefront that links out**: tagline, badges, one proof image, 6 to 11
   highlight bullets, install, a 4-command first run, a short feature tour where each item
   ends in "see the docs", then contributing and license (uv, Trivy, OSV-Scanner). The long
   READMEs (ripgrep, Ruff) are long because they inline reference; we should not.

What the evidence says about LLM discovery and SEO:

- llms.txt is cheap and documentation sites are its strongest case; coding agents fetch it,
  general crawlers mostly do not, and Google says Search does not use it. Do it, but do not
  rely on it. The things that move citation are the same things that move SEO: server-rendered
  HTML, one topic per page, the answer in the first two sentences, question-shaped headings,
  real tables, stable URLs, and a sitemap.
- Do not block the search and user-fetch crawlers (`OAI-SearchBot`, `Claude-SearchBot`,
  `Claude-User`, `PerplexityBot`) in robots.txt.
- Per-page markdown is what agents actually consume when they are pointed at a docs URL.

## Principles for our site

- **Every example is real output, generated by the binary.** An `xtask docs-examples` runs
  the release binary over a pinned demo fleet (`examples/demo-fleet.toml` plus a frozen OSV
  export) and writes the transcripts the pages include. CI fails when a transcript drifts.
  Nobody else in the category does this; it is also the strongest thing an LLM can quote.
- **One page answers one question**, with the answer in the first two sentences, then the
  command, then the output, then the details.
- **Lead with the fleet question** ("which one fix clears the most repos?"), never with
  "another vulnerability scanner".
- **Say what we are not**: no container/OS scanning (pair with Trivy), no server (pair with
  Dependency-Track), no advisory database of our own.
- Same voice as the docs today: plain, no em dashes, no hype words.

Each docs page also exists as markdown at the same path plus `.md` (and `index.md` for
directories), announced with `<link rel="alternate" type="text/markdown">`.

Use-case and compare pages are the SEO and LLM entry points: they match the questions people
type ("dependency vulnerability scan across all repos in a GitHub org", "osv-scanner vs
trivy", "find which repos use a vulnerable package"). Guides and reference are the depth
that makes the site worth citing.

## Page templates

- **Guide**: title as the task; a two-sentence answer; "You need"; numbered steps, each a
  command plus real output; "What just happened"; "Next" links. Question-shaped H2s.
- **Ecosystem**: files read (table: file, coverage level, notes), how versions are compared,
  known quirks, a real scan excerpt, links to the advisory sources.
- **Compare**: one-paragraph verdict, a feature table with honest cells, "Use X when",
  "Use fleetreach when", "Use both". Dated, with the versions compared.
- **Use case**: the problem in the reader's words, the outcome, the 3 to 5 commands, the
  output, the guides to read next.
- **Reference**: generated; never hand-edited (same rule as `crates/reach/README.md`).

## Landing page

Order: hero (tagline, one-line install with tabs, `fleetreach scan` on the demo fleet with
real output) → "One fix can clear many repos" (the impact view, real) → what it does, as 6
outcome tiles linking to guides → twelve ecosystems strip → accuracy proof (oracle results,
link to the concepts/accuracy page and the scripts) → "Works with" (GitHub, GitLab, Slack,
Dependency-Track, Trivy, SARIF) → compare strip ("pairs with Trivy, replaces a
Dependency-Track server for fleets") → three-line CI snippet → install again.

## Machine-readable layer

- `sitemap.xml` with `lastmod` from git; `robots.txt` that allows search and user-fetch bots
  and points at the sitemap.
- `llms.txt`: H1, one-paragraph summary, then H2 sections mirroring the nav, each link to the
  `.md` copy with a one-line note; `## Optional` for changelog and specs. `llms-full.txt` is
  the concatenated docs (we are small enough for one file).
- JSON-LD: `SoftwareApplication` (name, description, applicationCategory
  "SecurityApplication", operatingSystem, softwareVersion, license, codeRepository, offers
  price 0) on the landing page; `TechArticle` plus `BreadcrumbList` on docs pages; `FAQPage`
  on the FAQ.
- Per-page `<title>` "Task · fleetreach", a 150-character meta description, canonical URL,
  Open Graph image per section.
- An "agents" block on the landing page, as Deno does: "Read
  https://…/llms.txt and set up fleetreach for this org".

## README

Target about 150 lines, a storefront that links out:

1. Logo, 4 badges (crates.io, CI, MSRV, license).
2. One-sentence tagline plus one paragraph: the fleet question and the answer.
3. A real output image or block (the impact view on the demo fleet).
4. Highlights: 8 to 10 bullets (12 ecosystems, blast radius and remediation queue, verified
   fix PRs, SBOMs, licenses, SSVC/KEV, history and SLAs, reachability, fail-closed, no
   server).
5. Install (script, Homebrew, cargo, container).
6. First run: 4 commands with output.
7. Feature tour: 6 short sections, each one command plus "see the guide".
8. How it compares (5 lines, link to /compare).
9. Documentation, contributing, security policy, license.

Everything else that is in the README today moves into docs pages (the long `fleet.toml`
walk-through, exit codes, design decisions, architecture, reachability).

## Tooling decision

The current split (hand-written landing page plus mdBook) cannot produce per-page markdown,
JSON-LD, a sitemap or llms.txt without plugins. Options:

- **A. Astro Starlight (recommended).** One site for the landing page, docs, use cases and
  comparisons; sitemap and Pagefind search built in; `starlight-llms-txt` for llms.txt;
  per-page markdown via a plugin or a small build step; actively developed. Cost: a Node
  toolchain for the docs build only (the pure-Rust rule covers the crates, not the website).
- **B. Keep mdBook, add an xtask.** The xtask writes the sitemap, llms.txt, `.md` copies and
  JSON-LD after `mdbook build`. No new toolchain, but the landing, use-case and compare pages
  stay hand-written HTML outside the book, and theming two systems stays a chore.
- Material for MkDocs is in maintenance mode since November 2025; not considered.

Either way the reference pages are generated by an xtask from clap and the config schema,
and examples come from `xtask docs-examples`.

Also open: a custom domain (for example `fleetreach.dev`). GitHub Pages under
`tess-fun.github.io/fleetreach` works, but a domain we own keeps URLs stable if hosting
moves and reads better in citations. Decide before launch, since URLs should not change after.

## Phases

1. **Foundations**: generator choice, URL map, templates, `xtask docs-examples` with the
   frozen demo fleet, sitemap/robots/llms.txt/markdown copies, JSON-LD. Move existing pages
   across with redirects from the old mdBook URLs.
2. **Depth**: generated reference, the 12 ecosystem pages, all guides.
3. **Entry points**: use cases, comparisons, examples, FAQ, the new landing page.
4. **README rewrite** pointing into the new site.
5. **Checks in CI**: links, transcripts not drifted, every page has a description and is in
   the sitemap and llms.txt, Lighthouse SEO and accessibility at 100.

## Done when

- Every subcommand and every 1.5.0 feature has a guide or reference page with real output.
- `/llms.txt`, `/llms-full.txt`, `/sitemap.xml` and a `.md` copy of every docs page are
  served; robots.txt allows search crawlers.
- Lighthouse SEO 100 and accessibility at least 95 on the landing page and a sample of docs
  pages; no broken links.
- The README is under about 160 lines and every section links to the site.
- Asking a fresh LLM session "how do I find which of my repos are exposed to CVE-X" with only
  the llms.txt URL yields the right `fleetreach` command.
